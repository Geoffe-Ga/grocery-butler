# Capability API v2

The contract OpenClaw uses to operate Grocery Butler. Decided in
[ADR 0009](../adr/0009-capability-api-v2-contract.md). Base path: `/api/v2`.
`/api/v1` is unchanged and stays in service until OpenClaw has moved.

## Rules for every request

| Rule | Detail |
|------|--------|
| Authentication | `Authorization: Bearer <token>`, the same HMAC token as v1, bound to the request's method, path and body. The tailnet guard applies. The exact format, with fixed inputs and the tokens they must produce, is in [`auth-token-vectors.json`](auth-token-vectors.json): run your own token code against it. |
| Bodies | JSON objects, `Content-Type: application/json`, at most 1 MiB. Unknown fields are rejected. |
| Responses | JSON. Lists are wrapped in an object, for example `{"items": [...]}`. Times are ISO 8601 in UTC. |
| Correlation | Every response carries `X-Correlation-ID`. Send your own (8 to 64 letters, digits, hyphens or underscores) to find your request in the audit trail; anything else is replaced with a generated id. |

## Rules for every change

A change is any `POST`, `PATCH` or `DELETE`.

| Header | Rule |
|--------|------|
| `X-Household-Member` | The key of the active household member who is acting, for example `geoff`. Recorded as `geoff@<channel>`. The one exception: `POST /members` while the household has no active member (the first member, or after everyone was deactivated), when there is nobody to name. |
| `Idempotency-Key` | A unique value per change: 8 to 128 printable ASCII characters, no spaces. |

**Retrying.** Send the same request with the same `Idempotency-Key` and you
get the first response back, with `Idempotency-Replayed: true`, and nothing
changes. Only successful responses are stored. A request that failed changed
nothing, so retrying it runs it again. Records are kept for 30 days.

## Errors

Every error has this shape. Branch on `code`; show `message` to a person.

```json
{"error": {"code": "item_not_found", "message": "No household item has id 42.", "details": {}}}
```

| Status | Code | Meaning |
|--------|------|---------|
| 400 | `bad_request` | The body is not a JSON object, or the request is malformed. |
| 400 | `validation_failed` | A field is missing, unknown or invalid. `details.fields` lists each field and its problem. |
| 400 | `member_required` | A change was sent without `X-Household-Member`. |
| 400 | `idempotency_key_required` | A change was sent without `Idempotency-Key`. |
| 400 | `idempotency_key_invalid` | The key is too short, too long, or not printable ASCII. |
| 400 | `invalid_member_key` | A member key is not 1 to 32 lowercase letters, digits, hyphens or underscores. |
| 401 | `unauthorized` | The bearer token is missing or not valid for this exact request. |
| 403 | `member_unknown` | `X-Household-Member` names nobody active. |
| 404 | `not_found` | No such capability. |
| 404 | `item_not_found` | No household item has that id. |
| 404 | `member_not_found` | No household member has that key. |
| 404 | `observation_not_found` | No observation has that id. |
| 404 | `batch_not_found` | No observation batch has that id. |
| 404 | `need_not_found` | No replenishment need has that id. |
| 404 | `constraint_not_found` | No hard constraint has that id. |
| 400 | `constraint_invalid` | An allergen exclusion or dietary rule has no value, or do-not-substitute names no item. |
| 404 | `plan_not_found` | No shopping plan has that version, or no plan was built yet. |
| 404 | `recipe_not_found` | A meal names a saved recipe that does not exist. |
| 400 | `plan_invalid` | A recipe is listed more than once. Give it once with the servings you want. |
| 400 | `target_incomplete` | An item's target amount would be left with a quantity and no unit, or a unit and no quantity. Set both or clear both. |
| 405 | `method_not_allowed` | The capability does not support that method. |
| 409 | `idempotency_key_reused` | The key was already used for a different request. |
| 409 | `request_in_progress` | A request with this key is still running. Retry shortly. |
| 409 | `member_exists` | That member key is taken. |
| 409 | `alias_conflict` | The alias already names a different item. Merge the items if they are the same thing. |
| 409 | `alias_not_removable` | The alias is the item's own name, or not one of its aliases. |
| 409 | `merge_not_allowed` | The merge or unmerge breaks a rule in ADR 0006. The message says which. |
| 409 | `observation_superseded` | The observation was already corrected or retracted. Act on the row that replaced it. |
| 400 | `batch_invalid` | The batch is empty, has more than 200 proposals, or names the `system` source. |
| 409 | `batch_not_open` | The batch was already reviewed, rejected, or has expired. Submit a new one from fresh evidence. |
| 409 | `reviews_missing` | Some proposals have no decision. `details.proposal_ids` lists them. Nothing was recorded. |
| 409 | `review_invalid` | A decision can't be applied: it names a proposal outside the batch, names one twice, confirms a proposal that matched no item, or corrects onto an item that does not exist. Nothing was recorded. |
| 409 | `need_move_not_allowed` | The need can't move to that status from where it is (ADR 0008). The message lists what it can become. |
| 404 | `adapter_not_found` | No fulfillment adapter has that name in this deployment. |
| 404 | `approval_not_found` | No handoff approval has that id. |
| 404 | `handoff_attempt_not_found` | No handoff attempt has that id. |
| 400 | `handoff_not_available` | The adapter sends nothing outside the household and needs no approval (use the export), or the plan has no lines. |
| 409 | `plan_not_current` | The needs under the plan have changed. Build a new plan and hand that one off. |
| 409 | `approval_not_actionable` | The approval is not in the state this step needs: not yet approved, already executed, rejected or expired. Draft a new one. |
| 409 | `approval_hash_mismatch` | The hash sent is not the hash of the draft. Fetch the draft and show the member its current content. |
| 409 | `approval_stale` | The plan's needs changed after the draft was made. Nothing was sent. Build a new plan. |
| 409 | `approval_tampered` | The stored approval no longer matches what was approved. Nothing was sent. |
| 409 | `handoff_in_progress` | Another request with this key is still carrying the handoff out. Read the attempt. |
| 502 | `handoff_failed` | No handoff was created. `details.attempt` has the attempt, its `error_code` and `retryable`. |
| 404 | `receipt_not_found` | No receipt has that id. |
| 400 | `receipt_invalid` | The receipt has no lines, more than 200, or names a handoff attempt that does not exist. |
| 409 | `receipt_not_open` | The receipt was already confirmed or rejected. Submit a new one. |
| 409 | `receipt_review_invalid` | The review can't be applied: a line has no decision or two, a line matched no item and none was given, a substitution has no `fulfils_need`, or an item named does not exist. Nothing was recorded. |
| 413 | `payload_too_large` | The body is over 1 MiB. |
| 500 | `internal_error` | Something failed on the server. Nothing in the message is safe to parse. |

## Capabilities

### Household members

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /members` | List active members. `?include_inactive=true` lists everyone. | 200 `{"members": [...]}` |
| `POST /members` | Add a member. Body: `key`, `display_name`. | 201 member |
| `POST /members/{key}/deactivate` | Stop a member being named on new changes. Their history stays. | 200 member |
| `POST /members/{key}/reactivate` | Undo a deactivation. | 200 member |

A member: `id`, `key`, `display_name`, `active`, `created_at`, `created_by`.

### Household items and their current state

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /items` | List items with their state, sorted by name. `?q=` matches name, display name or alias. `?include_inactive=true` includes merged items. | 200 `{"items": [...]}` |
| `POST /items` | Find the item a name refers to, or create it. Body: `name`, optional `display_name`, `category`. | 201 if created, 200 if it existed |
| `GET /items/{id}` | One item with its aliases, state and open need. | 200 item |
| `PATCH /items/{id}` | Change `display_name`, `category`, `preferred_unit`, `staple_policy`, `preferred_brand`, `preferred_size`, `target_quantity`, `target_unit`, `cadence_days`. A field sent as `null` is cleared; a field left out is untouched. The item's need is brought in step with a new policy at once. | 200 item |
| `POST /items/{id}/aliases` | Give the item another name. Body: `alias`. | 200 item |
| `POST /items/{id}/aliases/remove` | Take a name away. Body: `alias`. | 200 item |
| `POST /items/{id}/merge` | Merge this item into another. Body: `into_item_id`. Open needs of the two are folded into one. | 200 surviving item |
| `POST /items/{id}/unmerge` | Undo a merge. | 200 restored item |
| `GET /items/{id}/history` | Why we believe what we believe: the item's identity events and every observation, superseded rows and retractions included. | 200 |

An item: `id`, `name`, `display_name`, `category`, `preferred_unit`,
`staple_policy`, `preferred_brand`, `preferred_size`, `target_quantity`,
`target_unit`, `cadence_days`, `active`, `merged_into_id`, and `state`. The
detailed form adds `aliases` and `open_need`.

`staple_policy` says how the household wants the item replenished (ADR
0017). It is one of these, or `null`:

| Policy | When it runs low or out | When a planned meal uses it |
|--------|-------------------------|-----------------------------|
| `always_keep` | A need is raised and approved by the policy itself. It is on the next plan. | Not added; it is kept in stock. |
| `replenish_when_low` | A need is suggested. A member approves it. | Not added; it is kept in stock. |
| `meals_only` | Nothing. | Added to the plan. |
| `never_suggest` | Nothing. | Not added. The plan lists it under `unplanned` with the reason. |
| `null` | A need is suggested. | Added to the plan. |

A member can ask for any item by name whatever its policy (`POST /needs`).

`target_quantity` and `target_unit` are an optional amount to buy when
nothing else states one. Set both or clear both; one without the other is
`400 target_incomplete`. `target_quantity` must be above zero and
`target_unit` one of the unit values (`each`, `bag`, `lb`, and so on).
`cadence_days` (1 to 365) is a hint for how often the item is usually
bought; nothing acts on it yet.

`state` is the item's snapshot (ADR 0007):

| Field | Meaning |
|-------|---------|
| `state` | `on_hand`, `low`, `out` or `unknown`. |
| `stated_state` | What was last stated, even when `state` is `unknown` because it went stale. |
| `stale` | Whether the latest observation is older than `fresh_for_days`. |
| `age_days` | Age of the latest observation. |
| `observation` | The observation behind the state: `actor`, `source`, `confidence`, `observed_at`, `notes`, and the rest. `null` when nothing valid was observed. |

Matching is deliberately weak (ADR 0006): names match after lowercasing and
collapsing spaces. "Tomato" and "tomatoes" are two items until a member adds
an alias or merges them. Never merge on a guess; ask.

### Observations

There are two ways for inventory evidence to arrive, and choosing the right
one matters.

- **A member said it.** "We're out of milk", typed or spoken by a person and
  understood without doubt. Record it directly.
- **A model inferred it.** Anything read off a photo, or parsed from a
  message with any doubt about the item or the state. Submit it as an
  observation batch. Nothing is recorded until a member reviews it.

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `POST /items/{id}/observations` | Record what the acting member says. Body: `state` (`on_hand`, `low`, `out`), optional `quantity` with `unit`, `observed_at`, `notes`. Recorded as `human` evidence, and the item's need is synced. | 201 observation |
| `POST /observations/{id}/correct` | Replace an observation with what should have been recorded. Same body. The old row stays in history. | 201 observation |
| `POST /observations/{id}/retract` | Withdraw an observation without stating anything in its place. Body: optional `notes`. | 201 observation |

A quantity is only ever something a person stated or a receipt showed, never
an estimate (ADR 0003). `unknown` can't be stated: it is what the state
becomes when there is no valid, fresh observation.

### Observation batches

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `POST /observation-batches` | Submit proposals for review. Body: `source` (`photo`, `human`, `receipt`, `order`), `proposals` (1 to 200), optional `evidence_ref`, `notes`, `observed_at`. Changes no inventory state. | 201 batch |
| `GET /observation-batches` | List batches, oldest first. `?status=` filters by `open`, `confirmed`, `rejected`, `expired`. | 200 `{"batches": [...]}` |
| `GET /observation-batches/{id}` | One batch with its proposals. | 200 batch |
| `POST /observation-batches/{id}/resolve` | Apply the member's review, all at once. Body: `reviews`, optional `accept_high_confidence`. | 200 batch |
| `POST /observation-batches/{id}/reject` | Throw the whole batch away. | 200 batch |

A proposal in a submission: `name` (what was seen, in your words), `state`,
`confidence` (0 to 1), optional `notes`. The name is matched to a household
item by alias. A name that matches nothing stays unmatched; it never creates
an item.

A proposal in a response adds `id`, `item_id` (the match, or `null`),
`decision`, and `needs_review`, which is `true` when the name matched
nothing or the confidence is below 0.8.

A review entry: `proposal_id`, `action`, and for a correction `item_id`,
`state`, or both.

| Action | Effect |
|--------|--------|
| `confirm` | Records the proposal as proposed, keeping the batch's source and evidence and the proposal's confidence. The proposal must have matched an item. |
| `correct` | Records the member's own statement of the right item and state, as `human` evidence. |
| `reject` | Records nothing. |

Every proposal needs a decision. `accept_high_confidence: true` confirms the
ones you left out, but only those with `needs_review: false`; ask the member
about the rest. If anything in the review is wrong, nothing is recorded and
the batch stays open. A batch not reviewed within 72 hours expires.

### Replenishment needs

A need says an item should be bought, why, and what the household decided
(ADR 0008). An item has at most one open need.

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /needs` | List needs, oldest first. Defaults to open ones. Repeat `?status=` to choose statuses. | 200 `{"needs": [...]}` |
| `GET /needs/{id}` | One need with its reasons and the history of its status changes. | 200 need |
| `POST /needs` | A member asks for an item. Body: `item_id`, optional `note`. Joins the item's open need, or starts one already `approved`. | 201 need |
| `POST /needs/{id}/approve` | The household wants this bought. Body: optional `note`. | 200 need |
| `POST /needs/{id}/defer` | Snooze. Body: optional `until` (a time) and `note`. With no `until`, it waits for a member. | 200 need |
| `POST /needs/{id}/reopen` | End a snooze early. | 200 need |
| `POST /needs/{id}/dismiss` | Don't suggest this again on the same evidence. | 200 need |
| `POST /needs/{id}/cancel` | It is no longer wanted. | 200 need |

Statuses: `suggested`, `approved`, `deferred`, `planned`, `ordered` (open);
`dismissed`, `received`, `cancelled` (closed). Inventory raises and withdraws
suggestions on its own. Only a member approves, defers or dismisses. Moving a
need to `planned`, `ordered` or `received` belongs to plans, handoffs and
reconciliation, which are not live yet.

### Shopping plans

The plan is what the household intends to buy: one line per item, with every
reason it is there (ADR 0011). It is built by plain code from the needs a
member approved and, optionally, saved recipes to shop for. No model takes
part, and the same inputs always give the same plan. Each plan is a numbered
version that never changes once stored.

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `POST /plans` | Build the plan. Body: optional `meals`, each `recipe_id` with optional `servings`. | 201 if a new version was stored; 200 if nothing changed and the latest version stands |
| `GET /plans` | List every version, oldest first: `version`, `content_hash`, `line_count`, `created_by`, `created_at`. | 200 `{"plans": [...]}` |
| `GET /plans/latest` | The current plan with its lines. | 200 plan |
| `GET /plans/{version}` | One version with its lines. | 200 plan |

A plan: `version`, `content_hash`, `meals`, `lines`, `unplanned`,
`created_by`, `created_at`, and `is_current`.

| Field | Meaning |
|-------|---------|
| `is_current` | `false` once the needs, recipes or items under this version changed. Build again before asking a member to approve anything. |
| `lines[].amounts` | What recipes asked for, summed within a unit dimension (cups with gallons, never cups with jars). Empty when only a need put the item on the plan: it means "the usual". |
| `lines[].reasons` | Every reason: `kind` (`low_stock`, `out`, `recipe_demand`, `manual_request`, `recurring_staple`), `source_key`, `detail`. Use these to answer "why is this on the list?". |
| `lines[].constraints` | The item's `preferred_brand` and `preferred_size`, when set. |
| `lines[].need_id` | The approved need behind the line, if there is one. |
| `unplanned` | Recipe ingredients that could not be planned, each with the `problem`. Tell the member; don't drop them silently. |

Building a plan moves the approved needs on it to `planned`. A suggestion
nobody approved is never on a plan. A recipe's pantry items, and the
household's pantry staples, add nothing on their own; when the household is
low on one, it arrives as a need like anything else.

### Hard constraints and soft preferences

Two different things, kept apart on purpose (ADR 0012).

- A **hard constraint** must hold: an allergen exclusion, a dietary rule, or
  "don't substitute this item".
- A **soft preference** is what the household would like: a brand, a size,
  organic, generic.

There is no way to turn one into the other. Never send an allergen as a
preference, and never treat a hard constraint as optional.

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /constraints` | List active hard constraints, with `common_allergens` to suggest. `?include_inactive=true` includes removed ones. `?item_id=` returns those that apply to one item. | 200 |
| `POST /constraints` | Add a hard constraint. Body: `kind` (`allergen_exclusion`, `dietary_rule`, `do_not_substitute`), `value`, optional `item_id` and `note`. Without `item_id` it holds for the whole household. | 201 constraint |
| `POST /constraints/{id}/deactivate` | Stop a constraint applying. Its record is kept, with who removed it. | 200 constraint |
| `GET /soft-preferences` | Household-wide stored preferences. `?item_id=` returns everything that applies to one item: its own brand and size, matching brand rules, and stored preferences. | 200 `{"preferences": [...]}` |
| `POST /soft-preferences` | Store a preference. Body: `kind` (`brand`, `avoid_brand`, `size`, `organic`, `generic`), optional `value` and `item_id`. | 201 |

What follows from a hard constraint:

- **It is on every plan line it applies to**, in `lines[].hard_constraints`
  (`kind`, `value`, `scope`). Household-wide constraints are on every line,
  because Grocery Butler doesn't know what a product contains.
  `lines[].constraints` holds soft preferences only.
- **Changing one makes the current plan stale.** `is_current` turns `false`;
  build again.
- **An adapter enforces it or reports it.** Each adapter lists the kinds it
  can guarantee in `enforces`. Every other hard constraint comes back on the
  handoff as `unenforced_constraints`. Tell the member about each one.
- **`do_not_substitute` needs an `item_id`** and takes no value.

The old free-text dietary restrictions were copied into one household
`dietary_rule`, lowercased but not reworded, and unverified. No adapter can enforce free
text. Ask the household to enter real allergens as `allergen_exclusion`.

### Fulfillment

A fulfillment adapter moves a plan toward a purchase the household completes
somewhere else (ADR 0001). Every adapter declares what it can do. Two rules
hold for all of them: a handoff is never an order, and a person always
finishes the purchase.

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /fulfillment/adapters` | List the adapters this deployment offers: `name`, `display_name`, `capabilities`, `authorization`, `data_freshness`, `human_required`, `enforces`. | 200 `{"adapters": [...]}` |
| `GET /plans/{version}/export` | Export a plan version as a list for any store. `?format=` is `text` (default), `json` or `csv`. | 200 export |

An export: `adapter`, `status` (`created`), `plan_version`,
`plan_content_hash`, `format`, `content`, `human_action` (the sentence to
tell the member what to do next), and `unenforced_constraints`. A list can
enforce nothing, so the export prints each hard constraint on its line as
`{MUST: ...}` and reports all of them as unenforced.

Exporting changes nothing and sends nothing anywhere, so it needs no
approval, no member header and no idempotency key. Handing a plan to a
service outside the household does need a member's approval, bound to the
exact plan version; that arrives with the first such adapter.

Capabilities an adapter can declare: `export_list`, `open_search`,
`shopping_list_link`, `draft_cart`, `deep_link_cart`, `read_cart`,
`read_order`, `import_receipt`. Only `export_list` is offered today. Don't
assume a capability an adapter doesn't list.

A deployment that sets `INSTACART_ENABLED=true` also lists an `instacart`
adapter with the single capability `shopping_list_link` (ADR 0014).

### Handoffs to an outside service

Sending a plan to a service outside the household takes three steps, so a
member sees exactly what leaves before it does (ADR 0016).

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `POST /plans/{version}/handoffs` | **Draft.** Body: `adapter`. Stores what the member must approve. Sends nothing. | 201 approval |
| `GET /handoffs/{id}` | Read an approval again. | 200 approval |
| `POST /handoffs/{id}/approve` | **Approve.** Body: `payload_hash`, the hash of the draft the member was shown. | 200 approval |
| `POST /handoffs/{id}/reject` | Turn it down. Optional body: `note`. | 200 approval |
| `POST /handoffs/{id}/execute` | **Execute.** Calls the adapter once and records an attempt. No body. | 201 attempt |
| `GET /handoffs/attempts/{id}` | Read one attempt. | 200 attempt |
| `GET /plans/{version}/handoffs` | List a plan version's attempts, oldest first. | 200 `{"attempts": [...]}` |

An approval: `id`, `status` (`draft`, `approved`, `executed`, `rejected`,
`expired`, `stale`), `plan_version`, `payload`, `payload_hash`,
`created_by`, `created_at`, `expires_at`, `approved_by`, `approved_at`. It
expires 30 minutes after it is drafted.

The `payload` is what to show the member, in full:

| Field | Meaning |
|-------|---------|
| `adapter`, `adapter_display_name` | Where the plan would go. |
| `plan_version`, `plan_content_hash` | Exactly which plan. |
| `lines` | Each line's `item_id`, `display_name` and `amounts`. |
| `unenforced_constraints` | Every hard constraint the adapter can't guarantee. **Read these to the member.** |
| `issues` | What the adapter's translation leaves out: `kind`, `item_id`, `display_name`, `detail`. |
| `approving_acknowledges_unenforced_constraints` | True when approving means the member accepts checking those constraints themselves. |

An attempt: `id`, `approval_id`, `adapter`, `plan_version`,
`plan_content_hash`, `status`, `external_url`, `open_path`,
`link_expires_at`, `opened_at`, `error_code`, `retryable`, `human_action`,
`summary`, `needs_your_check`, `sent`, `created_by`, `created_at`,
`updated_at`.

| Field | Use |
|-------|-----|
| `summary` | A sentence you can say to the member as it stands. It never claims a purchase. |
| `needs_your_check` | Short clauses, one per thing the member must check themselves: each unenforced hard constraint and each thing the translation left out. |
| `sent` | What was approved and sent: `lines`, `issues`, `unenforced_constraints`. |
| `open_path` | A path on Grocery Butler that records the link was opened and redirects to it. Give the member this instead of `external_url` when you can, so an opened link isn't later counted as abandoned. `null` when there is no live link. |

| Attempt status | Meaning |
|----------------|---------|
| `created` | The link exists. Give the member the link and say `summary`. |
| `opened` | A member followed the link through `open_path`. It says nothing about what they did next. |
| `failed` | No link. `error_code` says why. |
| `expired` | The link's time ran out. A new link needs a new draft and approval. |
| `pending` | A request is still working, or one crashed. Draft again if it stays. |

**Words to avoid.** Never tell the member anything was ordered, purchased,
bought, paid for, delivered or on the way, and never call Instacart a
partner. Use `summary`, or words that say only that a link is ready to
review (ADR 0020).

**A handoff is not an order.** `created` means a link exists. It says
nothing about whether anyone opened it or bought anything, and it changes no
need and no inventory.

**Retrying execute.** The request's `Idempotency-Key` is the attempt's key.
Send the same request again and you get the same attempt; nothing is sent
twice. The one exception is the useful one: if the attempt failed with
`retryable` true (the provider was unreachable or rate limited), the same
key tries again under the same approval, as long as the approval has not
expired and the plan has not changed. A different key can't reuse an
executed approval.

Error codes an attempt can carry: `provider_unavailable` (retryable),
`not_configured` (the deployment has no provider key; use the export),
`unauthorized`, `bad_request`, `invalid_response`, `adapter_error`.

### Check reminders

A reminder is a suggestion that the household look at one item: "is there
still coffee?". Grocery Butler chooses which few are worth asking; you
decide whether, when and how to ask (ADR 0019). Nothing here sends a
notification.

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /reminders/checks` | What could be asked now. Records nothing. | 200 overview |
| `POST /reminders/checks/issue` | Take the next reminders to surface and record them as issued. Optional body: `max` (0 to 20). Never returns more than today's remaining allowance. | 200 `{"issued": [...]}` |
| `GET /items/{id}/check-reminder` | What members asked for about this item's reminders, with the history. | 200 state |
| `POST /items/{id}/check-reminder` | Body: `action` (`snooze`, `dismiss`, `stop`, `resume`), and `days` (1 to 90) for a snooze. | 200 state |

The overview: `candidates`, `daily_limit`, `issued_today`,
`remaining_today`, and `suggested_hour_utc` (the hour the household usually
reports on its kitchen, or `null` until that is known; convert it to their
time zone).

A candidate: `item_id`, `display_name`, `policy`, `priority` (2 for
`always_keep`, 1 for `replenish_when_low`), `reason`, `age_days`,
`fresh_for_days`, `confidence`, `last_observation_id`.

| `reason` | Meaning |
|----------|---------|
| `never_checked` | Nobody has ever said whether there is any. |
| `stale` | The last observation is older than the item's freshness window. |
| `uncertain` | The last observation's confidence is below 0.8. |

Only items the household keeps in stock (`always_keep` or
`replenish_when_low`) are ever candidates.

| `action` | What the member means | Holds until |
|----------|-----------------------|-------------|
| `snooze` | "Not now." | `days` have passed. |
| `dismiss` | "I don't need to check that." | A new observation of the item arrives. |
| `stop` | "Stop asking about this." | A member sends `resume`. |
| `resume` | "Ask me again." | Clears every hold. |

**How to use it.** Call `issue` when you are about to ask, not when you are
only looking. Ask about what it returns, and record what the member says:
an observation if they answer, or a snooze, dismiss or stop if that is what
they tell you. An item you issued is not offered again for three days. The
household's limit is 3 a day unless they change the
`check_reminders_per_day` preference; 0 turns reminders off.

### Receipts

A handoff is a link; it says nothing about what came home. A receipt is how
the household tells Grocery Butler what actually happened (ADR 0018). Like
an observation batch, it is a proposal: nothing changes until a member
reviews it.

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `POST /receipts` | Store a receipt for review. Body: `lines` (1 to 200), optional `attempt_id`, `evidence_ref`, `notes`, `purchased_at`. Changes nothing else. | 201 receipt |
| `GET /receipts` | List receipts, oldest first. `?status=` is `open`, `confirmed` or `rejected`. | 200 `{"receipts": [...]}` |
| `GET /receipts/{id}` | One receipt with its lines. | 200 receipt |
| `POST /receipts/{id}/resolve` | Apply a member's review. Body: `reviews`, one per line. All of it applies, or none. | 200 receipt |
| `POST /receipts/{id}/reject` | Throw the receipt away. | 200 receipt |

A line to submit: `name` (the item as the receipt words it), `outcome`,
optional `quantity` with `unit`, `notes`, and `substitute_name` for a
substitution (required then, refused otherwise).

| `outcome` | Meaning | When confirmed |
|-----------|---------|----------------|
| `ordered` | It was on the order. Nothing has arrived. | The item's need moves to `ordered`. |
| `received` | It arrived. | The item is `on_hand` (source `receipt`). Its need is `received`. |
| `substituted` | Something else arrived in its place. | The substitute is `on_hand`. The wanted item's need is `received` if `fulfils_need` is true, or back to `approved` if false. |
| `refunded` | It was charged back or left off. | The item's need goes back to `approved`: still wanted. |

A stored line adds `id`, `item_id` and `substitute_item_id` (the matches, or
`null`), `decision` (`pending`, `confirmed`, `skipped`), `fulfils_need`,
`observation_id`, and `needs_review`. `needs_review` is true when the name
matched no item or the line is a substitution. A name is matched by alias and
never creates an item.

A review entry: `line_id`, `action` (`confirm` or `skip`), and where needed
`item_id` (which item the receipt meant), `substitute_item_id` (what
arrived) and `fulfils_need`. Every line needs exactly one entry.

**What to ask the member.** For each line with `needs_review`: "The receipt
says Dragonfruit. Which of your items is that, or should I skip it?" and
"Almond milk came instead of oat milk. Will that do, or do you still need
oat milk?" Never confirm a substitution, or guess an item, on the member's
behalf.

**Say what is known.** After a confirmed receipt you may say an item
arrived. Before one, a handoff means only that a link exists.

### Operations

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /operations/metrics` | Report how well the system is doing its job. | 200 metrics |

The metrics (ADR 0015):

| Field | Meaning |
|-------|---------|
| `extraction_failures` | Model replies that could not be turned into rows: `total` and `last_7_days`. |
| `adapter_failures` | Fulfillment handoffs that failed: `total` and `last_7_days`. |
| `correction_rate` | `decided` proposals, how many were `corrected`, and `rate` (0 to 1, or `null` when nothing was decided). |
| `stale_inventory` | Items whose last observation is past its freshness window. |
| `reconciliation_gaps` | Needs marked ordered more than 3 days ago and not yet received, plus handoffs created more than 3 days ago with no confirmed receipt. |
| `handoffs` | Counts of what became of handoffs: `created`, `opened`, `abandoned` (expired unopened), `reconciled` (a confirmed receipt points at it), `failed`, `corrected_before_handoff` (a draft rejected or gone stale). |
| `as_of` | When the numbers were read. |

A rising correction rate means proposals are getting worse. A rising stale
count means the household should be asked to check. Reading the metrics
changes nothing.

### Household data

| Method and path | What it does | Success |
|-----------------|--------------|---------|
| `GET /household/export` | Export every household table as one document. | 200 export |

An export: `format` (1), `dialect` (`sqlite` or `postgres`),
`schema_version`, `exported_at`, and `tables`, an object with one array of
rows per table. It is the household's whole record in plain text, so keep it
as carefully as the database. It is also the backup format (ADR 0013).

Reading it changes nothing, so it needs no member header and no idempotency
key. Deleting the household's data and restoring a backup are not API
capabilities. They are operator commands with a typed confirmation; see
[the data lifecycle runbook](../operations/data-lifecycle.md).
